# CommunicationBot — Telegram-бот магазина MVP

Python 3.11+. Детерминированный парсер, независимый каталог CSV/XLSX,
диалог оформления, SQLite и Telegram-бот на aiogram 3.x. LLM не используется;
внешний сервис — Telegram Bot API. Предыдущий `parser_mvp`, его CLI, тесты и
пакетные отчёты сохранены.

## С чего начать

Инструкция для первого запуска и работы покупателя/администратора:
**[START_HERE.md](START_HERE.md)**. Нужны Windows 11 и Python 3.11+.
После клонирования откройте терминал в корне проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-store.txt
Copy-Item .env.example .env
```

Заполните в `.env` токен своего бота и числовой Telegram ID администратора.
Для запуска дважды нажмите **START_BOT.bat**, для остановки — **STOP_BOT.bat**.
Они работают и из терминала Cursor: `.\START_BOT.bat`, `.\STOP_BOT.bat`.
Запуск загружает `.env`, проверяет Telegram API и не создаёт второй экземпляр.
Остановка проверяет путь, команду и время создания процесса; одного PID недостаточно.
После сообщения об успехе окно можно закрыть: бот продолжит работать в фоне.
Журнал запуска — `data/bot.stderr.log`, рабочая БД — `data/store.sqlite3`.
`.env`, `.venv`, PID, журналы и SQLite не входят в Git и создаются локально.
Не копируйте пример поверх уже настроенного `.env`.

Основной **учебный каталог работодателя — `catalog/mvp_catalog.csv`**.
Он подключён по умолчанию к CLI парсера, Telegram-боту и локальному симулятору
и содержит строго три предоставленных товара:

| Код | Товар | Цена | Размеры в наличии |
| --- | --- | --- | --- |
| T01 | Чёрная футболка | 2490 ₽ | S, M, L |
| T02 | Серое худи | 5990 ₽ | M, L |
| T03 | Синие джинсы | 6490 ₽ | Нет в наличии |

Наличие — снимок из предоставленного учебного файла, не живой склад.
Для T03 бот показывает название, цену и «Сейчас товара нет в наличии» с кнопкой
каталога; оформление и автоматическое предложение уточнить размер недоступны.
Отдельный вопрос о неизвестных сведениях можно передать человеку.
Материалы, доставка, оплата, возвраты и сроки
не указаны: бот предлагает оставить обращение и не придумывает ответ.
Старые `tests/fixtures/store_catalog.csv` и `parser_mvp_catalog.csv` остаются
синтетическими fixtures для регрессионных тестов и не подменяют основной каталог.
Заявка — обращение покупателя, не оплаченный заказ и не резерв товара.

## Установка: Windows 11, PowerShell

Из корня клонированного проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-store.txt
.\.venv\Scripts\python.exe -m pip check
```

Активация не требуется. Зависимости: RapidFuzz, openpyxl, aiogram 3.x;
pytest используется для тестов. Парсер отдельно по-прежнему устанавливается
через `requirements-parser.txt`. Зависимости пакета также объявлены в `pyproject.toml`.
При корпоративном CA используйте доверенное системное хранилище сертификатов;

## Автономный запуск без Telegram-токена

```powershell
.\.venv\Scripts\python.exe -m store_core simulate --db data/employer-demo.sqlite3
```

Симулятор использует те же `Shop`, SQLite и FSM, что и Telegram-адаптер:
выбор T01 → «Оформить заявку» → размер S → синтетическое имя → `demo@example.invalid` →
предпросмотр → подтверждение → заявка. Затем повторяет событие и кнопку,
имитирует первую ошибку уведомления, повторяет отправку и открывает БД заново.
Любое несовпадение проверок вызывает ошибку. В stdout возвращается JSON заявки
и проверок. Каждый самостоятельный запуск создаёт новую операцию оформления.
Данные демонстрации не смешиваются с рабочей БД по умолчанию.

```powershell
.\.venv\Scripts\python.exe -m store_core simulate --catalog catalog/mvp_catalog.csv --db data/simulation.sqlite3
```

Без токена работают загрузчик, парсер, бизнес-логика, хранилище, локальные
уведомления, симулятор и все тесты. Сам симулятор не импортирует aiogram.

## Архитектура

- `parser_mvp/` — чистая функция распознавания и загрузчик каталога.
- `store_core/service.py` — FSM и правила оформления, права администратора.
- `store_core/storage.py` — SQLite: `sessions`, `events`, `applications`.
- `store_core/notifications.py` — общий интерфейс отправки, локальный журнал,
  Telegram-отправитель, сохранение ошибки и повтор.
- `store_core/telegram.py` — aiogram Router/Dispatcher, личный чат и кнопки.
- `store_core/config.py` — переменные окружения.
- `store_core/simulator.py` — автономный end-to-end сценарий.
- `tests/store_core/` — каталог, FSM, БД, уведомления и aiogram без сети.

FSM реализована в бизнес-слое и хранится в SQLite, а не в MemoryStorage aiogram.
Aiogram `SimpleEventIsolation` последовательно обрабатывает события одного
диалога. Состояния ядра: `product`, `size`, `name`, `contact`, `confirm`,
`done`, `cancelled`; для передачи неизвестного вопроса — `human_offer`.
Каталог и вопросы PRICE/SIZES/AVAILABILITY показывают информацию без начала
оформления. Только ORDER или кнопка «Оформить заявку» переводят к выбору размера
либо имени. Приветствие после завершения показывает меню; во время оформления
сохраняет текущий этап. Информационный вопрос также не меняет незавершённые
данные. Возврат назад и отмена доступны кнопками и командами `/back`, `/cancel`.
Кнопки «Новое обращение» и «Каталог», как и явные команды `/start`, `/catalog`,
начинают новый диалог. Приветствие на этапе имени не записывается как имя.

В одной транзакции `BEGIN IMMEDIATE` сохраняются заявка, состояние диалога
и результат обработки события. `events.event_id` уникален; уникальны также
`applications.operation_id` и `confirmation_event`. Повтор Telegram update
возвращает сохранённый ответ; новое нажатие подтверждения завершённой операции
возвращает тот же ID заявки. Для повторного подтверждения проверяется конкретная
кнопка завершённой операции; любое другое сообщение не считается повтором.
Новый `/start` создаёт новый UUID операции.
Кнопки связаны с текущей операцией и показанным набором вариантов; устаревшие
кнопки отклоняются. Перед финальным подтверждением товар и размер проверяются
по текущему каталогу повторно.

## Подключение настоящего каталога

Задайте `CATALOG_PATH` или передайте `--catalog` симулятору/CLI парсера.
Бот также принимает `--catalog`; путь по умолчанию определяется относительно
корня исходного проекта, а не текущей рабочей папки. Никакого автоматического
переключения на синтетические товары при ошибке нет.

CSV: UTF-8 с необязательным BOM, разделитель `;` или `,`.
XLSX: ровно один лист; первая строка — заголовки, далее значения без формул.
Формулы отклоняются, поскольку openpyxl не пересчитывает их. Сохраните результат
формул как значения. Лишние колонки игнорируются; дубли известных колонок,
несколько синонимов одного поля, неоднозначный разделитель, некорректные строки
и повторяющиеся ID дают диагностическую ошибку. Неизвестные обязательные
заголовки нужно явно переименовать, загрузчик не угадывает их смысл.

| Поле | Заголовки | Правила |
| --- | --- | --- |
| ID | `product_id`, `id`, `артикул` | Обязателен, уникален |
| Название | `name`, `название`, `наименование` | Обязательно |
| Цена | `price`, `цена` | Необязательна, Decimal, без отрицательных/NaN |
| Валюта | `currency`, `валюта` | Необязательна, не подставляется по умолчанию |
| Размеры | `sizes`, `размеры` | Значения через `\|`, повторы отклоняются |
| Размеры в наличии | `sizes_in_stock`, `размеры в наличии` | Вместо `sizes`; пустая ячейка означает отсутствие товара в наличии |
| Цвет | `color`, `цвет` | Необязателен |
| Алиасы | `aliases`, `алиасы` | Через `\|` |
| Видимость | `active`, `активен` | Пусто/1/true/да — включён; 0/false/нет — выключен |

Для цены допускается точка или запятая, без разделителей тысяч и символа
валюты. В CSV с запятой десятичную запятую нужно заключать в кавычки.
Явные заголовки `price_rub`, `цена руб`, `цена, руб.`, `цена (руб.)`,
`price_usd`, `price_eur` задают RUB/USD/EUR; противоречащая валюта строки
отклоняется. `price` без валюты остаётся ценой с неизвестной валютой.
Если цена отсутствует, бот предлагает передать вопрос человеку.

В основном файле используется именно `sizes_in_stock`. Такой заголовок
явно устанавливает `stock_known=True`: S/M/L означают размеры в наличии,
а пустая ячейка T03 — подтверждённое отсутствие. Старые `sizes`/`размеры`
задают только известные размеры и **не** подтверждают наличие или отсутствие.
Оба заголовка одновременно запрещены как неоднозначное описание одного поля.
Дополнительных остатков, количеств и характеристик в основной файл не добавлено;
алиасы содержат только предоставленный код и тот же товар с переставленными словами.

Все товары остаются в модели Catalog, но отключённые исключены из поиска,
покупательского меню и оформления. `load_catalog()` каждый раз читает файл;
бот использует проверенный снимок до `/admin_reload` или перезапуска.
Администратор меняет CSV/XLSX в редакторе и выполняет `/admin_reload`:
ошибка нового файла сохраняет прежний рабочий каталог. Встроенный редактор
товаров пока не реализован.

## Telegram и конфигурация

`.env.example` содержит список настроек без секретов. Прямая команда
`python -m store_core bot` **не загружает `.env` автоматически**: она читает
переменные окружения. Поставляемый `START_BOT.bat` загружает `.env` сам.
Для прямого запуска без BAT задайте переменные в текущем PowerShell:
Токен получите у BotFather; для администрирования нужен числовой Telegram user ID,
не username и не ID группы. Администратор должен предварительно открыть бота
и отправить `/start`, чтобы бот смог отправить ему уведомление.

```powershell
$botToken = Read-Host "Токен BotFather" -AsSecureString
$env:TELEGRAM_BOT_TOKEN = [System.Net.NetworkCredential]::new("", $botToken).Password
$env:TELEGRAM_ADMIN_ID = Read-Host "Числовой Telegram user ID администратора"
$env:CATALOG_PATH = "catalog/mvp_catalog.csv"
$env:SQLITE_PATH = "data/store.sqlite3"
$env:NOTIFICATION_BACKEND = "telegram"
$env:STORE_TEST_MODE = "0"
$env:NOTIFICATION_FAIL_FIRST = "0"
.\.venv\Scripts\python.exe -m store_core bot
```

Токен вводится скрыто, не записывается в Git или логи приложения.
Для завершения — Ctrl+C. Без токена команда бота завершается понятной ошибкой;
симулятор и тесты от токена не зависят. Оформление и администрирование доступны
только в личном чате, чтобы контакты не попадали в группы.

| Переменная | По умолчанию |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | пусто |
| `TELEGRAM_ADMIN_ID` | не задан; административный доступ закрыт |
| `CATALOG_PATH` | `catalog/mvp_catalog.csv` относительно корня проекта |
| `SQLITE_PATH` | `data/store.sqlite3` |
| `NOTIFICATION_BACKEND` | `local` (альтернатива: `telegram`) |
| `STORE_TEST_MODE` | `0` |
| `NOTIFICATION_FAIL_FIRST` | `0`, при `1` требует тестового режима |

Это значения по умолчанию в Python. В `.env.example` выбран `telegram`, чтобы
после заполнения токена и admin ID уведомления приходили администратору.

## Покупатель

1. `/start` или `/catalog` — каталог с постраничным выбором.
2. Выберите товар: бот покажет только известные цену, валюту и размеры.
3. Нажмите «Оформить заявку», затем выберите размер; отсутствующий размер не заменяется ближайшим.
4. Введите имя и контакт: телефон из 7–15 цифр (можно +, пробелы, скобки,
   дефисы), email либо `@username` от 5 до 32 символов.
5. Проверьте данные и нажмите «Подтвердить». До этого заявка не создаётся.
6. `/start` — новое самостоятельное оформление; `/cancel` — отмена, `/back` — назад.

Свободные вопросы распознаются существующим парсером, например
«Хочу купить чёрную футболку M». RapidFuzz показывает кандидатов и требует
явного выбора товара. Информационный вопрос после выбора кандидата остаётся
информационным. Приветствие и непонятный текст на выборе размера сохраняют
оформление и предлагают продолжить его; XL или «размер XL» проверяются отдельно.
Нераспознанные и неподдерживаемые вопросы, в том числе
о доставке, оплате, возврате и материалах, передаются человеку только после отдельного выбора,
ввода контакта и финального подтверждения. Исходный вопрос сохраняется.
В учебном каталоге наличие явно указано колонкой `sizes_in_stock`. Недоступный
размер не заменяется другим; стандартная заявка на такой вариант не создаётся.
У старого каталога с колонкой `sizes` наличие остаётся неизвестным.
Из карточки можно нажать «Уточнить у человека». Явный вопрос на этапе выбора
размера также обрабатывается парсером; имя и контакт вводятся последовательно.

## Администратор и уведомления

`/admin` открывает меню: заявки, неотправленные уведомления, счётчики, каталог.
Права проверяются **при каждой команде и callback** по `from_user.id`.
`/admin_reload` проверяет права отдельно. Обычный пользователь не получает
данные даже при ручной отправке callback.

Команды:

- `/admin list` — заявки, страницы по 5 (также `/admin list 1` — следующая).
- `/admin view 1` — детали заявки №1, контакт, вопрос, состояние уведомления.
- `/admin status 1 2` — статус заявки №1: 0 — `Новая`, 1 —
  `Нужен ответ человека`, 2 — `Обработана`. Другие статусы запрещены БД.
- `/admin pending` — неотправленные (`pending` и `failed`).
- `/admin retry 1` — повтор уведомления для заявки №1.
- `/admin stats` — всего, по статусам и до 30 групп товаров.
- `/admin catalog` — карточки первых 15 активных товаров; полный выбор в `/catalog`.
- `/admin_reload` — проверить и загрузить обновлённый файл.

Заявка сначала фиксируется в БД со статусом уведомления `pending`, затем
отправляется уведомление. При ошибке заявка остаётся, сохраняются `failed`,
тип ошибки и число попыток. Тексты сетевых исключений не сохраняются: они
могут содержать секреты. Успех записывает `sent` и время отправки; уже успешно
отправленная заявка повторно не отправляется при обычном повторе команды.
После перезапуска неотправленные видны в меню и доступны для ручного повтора.
Автоматический фоновый повтор пока не реализован.

`NOTIFICATION_BACKEND=local` записывает только время и ID заявки в
`notifications.log` рядом с БД — без имени и контакта. `telegram` отправляет
детали назначенному администратору. Эти реализации используют один интерфейс.
Доставка уведомлений имеет семантику **at-least-once**: при аварии после
доставки в Telegram, но до отметки `sent`, повтор может отправить уведомление
снова. Уникальность самой заявки обеспечивается отдельно.

Для контролируемой ошибки первой попытки каждой заявки:

```powershell
$env:STORE_TEST_MODE = "1"
$env:NOTIFICATION_FAIL_FIRST = "1"
```

Без тестового режима такая настройка отклоняется. В симуляторе ошибка
включена явно только для демонстрации и не меняет рабочую конфигурацию.

## Сохранность данных

SQLite содержит заявки с ID, временем UTC, именем, контактом, Telegram user ID,
подтверждённым товаром и его названием, размером, одним из трёх статусов,
исходным вопросом, UUID операции, ID события и состоянием уведомления.
В БД также хранятся незавершённые диалоги и результаты обработки событий.
Завершённые сессии очищаются от дополнительных копий имени и контакта;
результаты событий могут содержать предпросмотр, поэтому вся БД приватна.

`data/`, `reports/`, `.env`, журналы, SQLite и WAL/SHM-файлы исключены из Git.
Рабочая БД по умолчанию `data/store.sqlite3`, демонстрационная —
`data/simulation.sqlite3` либо путь из `--db`. Старые отчёты не удаляются.
Ограничьте доступ к папке данных средствами ОС. База не зашифрована.
Запускайте **один процесс бота на один файл SQLite**. Журнал событий пока
хранится без срока очистки; резервирование и политика удаления данных —
задача следующего этапа. ID update предполагаются в рамках одного бота;
для другого токена используйте отдельный файл БД.

## Совместимый CLI парсера

Без `--catalog` используется основной учебный каталог; путь можно указать явно:

```powershell
.\.venv\Scripts\python.exe -m parser_mvp single --text "Сколько стоит чёрная футболка?"
.\.venv\Scripts\python.exe -m parser_mvp single --catalog catalog/mvp_catalog.csv --text "Есть синие джинсы M?"
.\.venv\Scripts\python.exe -m parser_mvp batch --catalog catalog/mvp_catalog.csv --input examples/store_core/catalog_questions.jsonl --output reports/employer-catalog
```

Регрессия на сохранённых синтетических данных предыдущего этапа:

```powershell
.\.venv\Scripts\python.exe -m parser_mvp single --catalog tests/fixtures/parser_mvp_catalog.csv --text "Есть ли футболка синяя XXL?"
.\.venv\Scripts\python.exe -m parser_mvp batch --catalog tests/fixtures/parser_mvp_catalog.csv --input examples/parser_mvp/reviewed.jsonl --output reports/parser-mvp/reviewed
```

`parse_message(text, catalog, state=None, *, config=None)` сохраняет обязательные
поля `intent`, `product_id`, `size`, `match_status`, `needs_clarification`,
`reason` и диагностические поля. Намерения строго: PRICE, SIZES, AVAILABILITY,
ORDER, CATALOG, UNKNOWN. «Сколько стоит доставка футболки?» остаётся UNKNOWN.
Точное название/алиас подтверждает товар; fuzzy и неоднозначность оставляют
`product_id=null` и возвращают кандидатов. Контекст `{"product_id":"..."}`
используется только при отсутствии названия в новом вопросе.

Дополнительные поля:

| `size_status` | Значение |
| --- | --- |
| `absent` | В поддерживаемом запросе нет распознаваемого указания размера |
| `recognized` | Размер распознан по каталогу; если товар определён, он есть у этого товара |
| `unavailable` | Для подтверждённого товара такого размера нет; известный размер либо безопасно распознанное обозначение |
| `unrecognized` | Обозначение неизвестно или указано несколько размеров; нужен ввод/выбор |

Для подтверждённого товара дополнительно возвращаются:

- `price` — строка точного Decimal либо null; `currency` — исходная валюта либо null.
- `available_sizes` — массив размеров в наличии при `stock_known=True`,
  пустой массив при подтверждённом отсутствии; null при неизвестном наличии.
- `availability` — `in_stock`, `out_of_stock` или `unknown` для товара в целом.
  Для запрошенного размера отдельно проверяется `size_status`: наличие худи
  размеров M/L не означает наличие запрошенного S.

Fuzzy-кандидаты и неизвестные вопросы не получают цену/наличие как будто товар
уже подтверждён. Пример T03: `price="6490"`, `currency="RUB"`,
`available_sizes=[]`, `availability="out_of_stock"`; при запросе M —
`requested_size="M"`, `size_status="unavailable"`.

`requested_size` сохраняет извлечённое обозначение (несколько — через `|`),
при отсутствии равно null. Для UNKNOWN/CATALOG извлечение размера не выполняется,
`size_status=absent`: это не заключение о содержимом неподдерживаемого вопроса.
Старое `size` сохраняет прежнюю семантику: глобально известный XL может
оставаться в `size` при `size_status=unavailable` для конкретного товара.
Используйте новый статус для валидации. Числовые размеры в свободной фразе
требуют слова «размер», чтобы не путать их с моделью/ценой.

Пакетный режим создаёт `json/*.json`, `results.csv`, `summary.json`, `reports.zip`.
PASS сравнивает только явно заданные `expected`-поля; отсутствие ожиданий —
UNREVIEWED. Для TXT доступен `--expected` JSON с ключами физических строк.
Коды возврата: 0 — нет FAIL, 1 — есть FAIL, 2 — ошибка входа.
Посторонние файлы не включаются в ZIP; CSV экранирует формульные префиксы.

## Проверки и ограничения

Итоговая проверка 20.11.2026: **337 PASS, 0 FAIL**. Все пять обязательных
сценариев ниже прошли через aiogram Dispatcher с изолированным транспортом и
временной SQLite. Отдельно проверены свободные запросы, недоступные размеры,
противоречие цвета/категории и сохранение текущего товара при оформлении.
Последние три исправленных свободных запроса также проверены пользователем
в реальном Telegram; автоматические тесты не подменяют эту ручную проверку.
Рабочая SQLite, локальные журналы и полные отчёты не публикуются.

```powershell
.\.venv\Scripts\python.exe -m pytest tests -q
.\.venv\Scripts\python.exe -m pytest tests/store_core/test_telegram.py -k required -v
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m compileall -q parser_mvp store_core
```

Прежние тесты парсера сохранены. Новые проверяют CSV/XLSX, Decimal, видимость,
структурированные размеры, оформление, неизвестный вопрос, отмену, возврат,
устаревшие кнопки, изменения каталога, повтор события/кнопки, конкурентные
подтверждения, уникальные ограничения SQLite, перезапуск, повторное
самостоятельное обращение, ошибки/повторы уведомлений и права администратора.
Aiogram проверяется через настоящий Dispatcher и fake transport: Telegram API
и действующий токен для тестов не нужны.

Пять обязательных сценариев исходного тестового задания проверяются
тестами `test_required_1_...` — `test_required_5_...` в
`tests/store_core/test_telegram.py`, строго на `catalog/mvp_catalog.csv`:

1. T01, размер M → подтверждение → запись SQLite → Telegram-уведомление
   администратору через поддельный транспорт. Транспорт проверяет, что запись
   уже сохранена до отправки.
2. T02, размер S → сообщение об отсутствии → обычная заявка не создаётся.
3. Вопрос о составе ткани T01 → отдельное согласие → контакт и подтверждение →
   статус «Нужен ответ человека», исходный вопрос сохранён и отправлен администратору.
4. Повтор одного Telegram update и повторное нажатие → одна запись и одно
   уведомление; повторное открытие SQLite сохраняет данные. Самостоятельное
   новое оформление того же покупателя создаёт другую заявку.
5. Ошибка Telegram-отправителя → заявка остаётся, сохраняется `failed` и ошибка →
   администратор повторяет отправку → `sent`, без новой заявки.

Дополнительно `tests/store_core/test_employer_catalog.py` проверяет точное
содержимое трёх товаров, цены, размеры, T03 без наличия, неизвестный товар,
доставку/оплату/возврат/состав ткани, явную семантику stock-колонки CSV/XLSX
и основной каталог по умолчанию. Базы старых запусков не переиспользуются
для демонстрации нового каталога; схемы и старые заявки не изменяются.

Реальный polling и доставка настоящему администратору требуют токена и сети;
проверки с настоящими Telegram-серверами не подменяются автономными тестами.
В ограниченном Windows sandbox даже автономному asyncio может потребоваться
разрешение на служебный локальный socketpair.

Не реализованы оплата, склад, резерв, доставка, веб-панель, встроенное изменение
товаров, автоматические повторы уведомлений и фоновые импорты каталога.
Подтверждение нового файла не сохраняет историю его цен; заявка сохраняет
идентификатор и название товара, а не финансовый документ. Полной морфологии
и произвольного понимания текста нет; правила распознавания консервативны.
Перед использованием за пределами учебной демонстрации нужны резервное
копирование и политика хранения данных.
